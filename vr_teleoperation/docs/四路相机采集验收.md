# 四路相机采集验收

更新：2026-11-21。主线目标是可靠采集，不是凑齐四张图。
本轮没有启动机器人、CAN/串口、驱动安装或主机重启。

## 先看操作入口

使用 `../local/four_camera/README.md`，不要启动旧 DJI 三路真实入口。
正常照明和任务视野通过之前，只运行 mock 或 camera-diagnostic。
相机服务健康中的 `ready` 明确只表示传输就绪，不表示画质或曝光同步通过。
`basic_image_ready` 另行拒绝近黑画面/检查失鲜，真实入口在 `ROBOT` 输入前后
及真实桥接开始/记录中强制检查，人工确认标志不能绕过；但它不能代替现场审片。

1. 核对 Expansion UUID/ext4/余量和四个物理端口，无其他取流进程。
2. 以实际采集照明预热，检查四路方向、把手/方块/抽屉内部及释放阶段可见性。
3. 核对实际单条时长的录制和落盘，不额外强制 120 秒压测；新硬件错误、卡死、95°C 软件停测、
   图像解码失败、序号缺口或接口恢复失败，立即停止升级测试并保留证据。
4. 用真实相机＋明确标记的合成关节跑 Recorder，核对每张 JPEG 与时钟侧车、
   起止边界、metadata 提交和重新读回。它不是机器人同步或真实示范。
5. 上述通过后，另在明确授权和现场安全条件下验 VR/双臂真实链路。
   A 启动并 ALIGNED 后才 X 开始，再 X 成功结束；B 停臂并记失败。
6. 保存确认后再复位，先少量人工审片，再决定批量采集。不要边保存边开始下一条。

## 需要通过什么

| 项目 | 当前方案/验收 |
| --- | --- |
| 身份 | by-path 物理端口＋VID/PID；重复 serial 和 videoN 不作角色依据 |
| 方向 | 全局/左右腕各一次 180°；胸部不旋转，预览/存盘/部署一致 |
| 帧率 | 目标四路 720p/30；滑窗实测 28.5–33 fps，不能只读设备声明 |
| 完整性 | 记录中不允许源序号缺口/重置；原生坏帧为 0，发布集合等于存盘集合 |
| 时序 | 保留真实源序号和接收时钟；因果选帧明示帧龄/跨度，不按帧号硬配对 |
| 画质 | 正常照明下无黑屏，关键物体/接触区细节可见；运动模糊和亮部饱和逐路检查 |
| 曝光 | 使用读回确认的参数；高帧率与亮度/噪声需要共同满足，不靠后处理拉亮掩盖 |
| 存储 | UUID/ext4 检查；原子图像发布，结束 fsync 数据/目录/侧车后提交 metadata |
| 恢复 | 异常条目保留；不自动续写，先只读核验；接口恢复、服务重开和整机重启分开验 |
| 主机 | 逐级测试且无新硬件错误；短测未复现不能宣称原卡死原因已修好 |

50 ms 匹配跨度、200 ms 新鲜度与帧率 95% 下限是当前工程门槛，
不是摄像头规格、机器人安全认证或已证明足以完成所有快速动作的训练指标。
原先的 85°C 停测已取消，85°C 只记录提醒；当前 6800H 以 AMD 标注的 95°C
Tjmax 为参考保留软件停止线，不关闭硬件温控，不把日志提醒判成相机不合格。
抽屉任务可以先选 20 Hz 时间网格，最终仍要按任务动作速度审片；
不能因四路名义帧率相同就宣称曝光时刻一致。
当前真实关节门控核对新鲜度、边界和四个输入非空；合成诊断的已知各 30 行计数
不等于已证明真实 250 Hz 关节流完全无漏样，后者仍需真实链路单独验收。

## 当前发现与取舍

- 四路此前均启用 Exposure Dynamic Framerate；Linux 文档明确该开关允许自动曝光
  动态改变帧率。临时设 0 可限制此行为，但仍要在正常照明和实际画面带宽下验证。
- 2026-11-20 夜间同样黑画面的短对照：原设置约 10 fps；关闭该项约 29.9 fps，
  没有序号缺口。手动 10 ms 对照也黑。不能从这些结果证明正常照明画质合格。
- 暂定源配置 1280×720 / 30 fps / payload 1280 / ae_priority 0，
  手动曝光、gain 仍未选定。native 每次先保存/读回，正常退出恢复原控制值。
- 早先有光照时四路 payload 1600 启动失败，内核报告带宽不足；
  payload 1280 可收图但实际帧率不齐。当前暗场 JPEG 很小，
  不可拿夜间短测代替正常场景吞吐验收。
- 图像旋转后的重新 JPEG 编码只减少/增加接收之后的数据量，
  不能修复相机到主机这一段已发生的 USB 带宽不足。

2026-11-21 只读枚举确认四台在 720p MJPEG 下仅声明 30/60 fps，
不能假定支持 25/20 fps。当前正常照明约 30 秒已实测四路约 29.91 fps，
不再为降低 CPU 或温度而扩大参数试验；只有实际任务出现掉帧、积压等问题时再针对修复。
需要改分辨率时先查设备支持，改接 USB 控制器仍需单独授权。
换到同一个集线器的另一孔不等于增加总带宽；不先购买设备或自动改接线。
保留异步真实时间戳比重复旧帧凑齐 30 fps 更重要。
确需更严格曝光同步时，应先核实具体整机型号是否支持触发/同步，再做光学事件
和时延验证；不能凭 OV4689 传感器宣传参数推断当前 USB 模组已经具备同步。

## 参考的开源处理方式

以下是 2026-11-20 查阅的官方资料/项目源码，不是给现有硬件的验收背书：

- [OpenArm WebXR 采集](https://docs.openarm.dev/tutorial/data-collection-webxr/) 与
  [OpenArm Dataset](https://docs.openarm.dev/dataset/)：保留原格式和官方控制节点，
  本地适配增加采集门控、四路和持久化，不改底层控制参数。
- [Diffusion Policy real_env.py](https://github.com/real-stanford/diffusion_policy/blob/main/diffusion_policy/real_world/real_env.py)：
  相机与机器人独立采样、缓存历史、以时间戳选择观测，并区分采集率与策略率。
- [UMI bimanual_umi_env.py](https://github.com/real-stanford/universal_manipulation_interface/blob/main/umi/real_world/bimanual_umi_env.py)：
  使用多相机缓存、接收时延参数和基于时间的观测选取，不把每次循环读相机视为硬件同步。
  本项目不照搬其特定采集卡重置逻辑。
- [LeRobot OpenCV 相机](https://github.com/huggingface/lerobot/blob/main/src/lerobot/cameras/opencv/camera_opencv.py)：
  后台读取、预热、超时、明确释放资源；仅取最新帧适用于实时观测，
  本项目完整原始录制另用独立游标 drain，避免 preview 消费 Recorder 帧。
- [Linux 相机控制](https://www.kernel.org/doc/html/latest/userspace-api/media/v4l/ext-ctrls-camera.html)：
  auto exposure priority 的动态帧率含义、曝光 100 µs 单位及曝光与帧间隔约束。

## 仍不能宣称完成

实际任务运动模糊/关键区域可见性、真实机器人与相机联采、
光学曝光时延/同步、Quest 当前头显版本验证、主机卡死根因与整机重启恢复。
正常照明约 30 秒的真实图像＋合成关节完整录制已经通过；下一步优先一条现场完整试采，
不要求先查明所有历史故障或完成任意时长压力测试。
允许继续做相机和离线检查，不代表允许机械臂运动或自动重启。
