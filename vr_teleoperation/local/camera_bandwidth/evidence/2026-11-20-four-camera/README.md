# 2026-11-20 四路微雪诊断与重启后核验

结论：四路可在候选 payload=1280 下同时取流，但**未通过正式采集验收**。
存在帧率差异、序号缺口，以及主机异常重启后的一张 0 字节文件。
本轮只获相机授权，未打开 CAN/串口、未发送机器人命令、未启动正式任务采集。

## 同日离线改善：预览与保存

偏暗原因已核对：初版标准方向预览取了每路开流第一帧，
前面的独立抓图取 FFmpeg `n=30`，即第 31 帧，不是同一启动阶段的公平对比。
同一段原始 JPEG 内，约半秒后已明显变亮；旋转/重编码没有造成这一级亮度下降。

| 身份 | 首帧平均灰度 | 同帧旋转/重编码后 | 约 2 秒平均灰度 |
| --- | ---: | ---: | ---: |
| global | 33.568 | 33.604 | 123.017 |
| wrist_right | 23.279 | 23.281 | 116.752 |
| wrist_left | 23.214 | 23.215 | 120.549 |
| chest | 35.359 | 35.359 | 122.666 |

灰度范围 0–255，是图像数字值，不是曝光 EV 或照度测量。
变化符合自动曝光/增益收敛的表现，但未记录控制值，不能确定具体参数，
也不能排除两次取图间现场光照/位置变化。后段约 12%–23% 灰度像素达到 250 以上，
白柜体亮部有饱和风险，不能因换一张更亮的图就宣称画质通过。

最新 `confirmed-layout-preview-warm.jpg` 选开流约 2 秒后的真实帧，无人工拉亮。
对照图为 `startup-vs-warm-preview.jpg`，数字为 `brightness-comparison.json`。
2 秒是明确的预览策略，不是自动曝光稳定或正式采集准备状态的证明。
不足预热时间时明确报告无 warmed preview，但仍独立核验文件完整性。

保存端已离线改进：

- JPEG 先写同目录独占 `.partial`，完整关闭后原子发布，不覆盖同名图像。
- 流内不逐帧 fsync，以免同步等待拖慢机械硬盘；此时尚不承诺已持久化。
- 结束时同步本条图像/Parquet、原始时钟侧车和目录，再原子提交并同步 metadata，
  完成前不发 `ended:success`。诊断报告同样不能提前标 complete。
- 保存/同步/metadata 失败保留证据并报失败，不伪装成功。
- fsync 是请求文件系统/设备完成同步，不是抗任意硬件故障的保证；
  未做真实掉电/重启故障注入，未重开四路相机验证吞吐。
- 94 项 Python 离线测试及 Recorder 合成数据端到端检查通过，
  摘要见 `offline-improvements-verification.json`。

中间一次 mock 曾右臂 action/obs 各缺 tick=1，证据保存在 `offline-missing-row/`，
没有靠重采或补帧掩盖。Recorder 订阅改为有界缓冲，mock 新增已知发送计数约束，
最终四路各 30 行且逐数组核对通过。没有证明真实采集永久无丢包，也没有包级根因结论。

保存语义：https://man7.org/linux/man-pages/man2/fsync.2.html
曝光控制：https://www.kernel.org/doc/html/latest/userspace-api/media/v4l/ext-ctrls-camera.html

## 测试经过

1. 四路逐一以 MJPEG、1280×720、请求 30 fps 抓图，均得到可解码的单帧。
   FFmpeg 仍出现 MJPEG APP 字段警告，见 `port-*-sample.stderr`，不能以样图掩盖告警。
2. 原双腕 payload=1600 的约 5 秒基线：分别 120 帧，约 24.33 / 23.88 fps，
   交付帧解码成功、库层序号无缺口。见 `pair-existing-p1600.*`。
3. 四路都用 1600 时第四路启动失败。内核明确记录
   `Not enough bandwidth for altsetting 8`；见 `four-p1600*`。
   失败不被清除，不能把它算为四路 5 秒通过。
4. 四路都用 1280 时完成约 60 秒共同取流。分辨率和请求帧率不变，
   仅修改本进程 UVC payload；没有改系统 uvcvideo 模块、udev 或固件。
5. 另做约 5 秒原始 JPEG 落盘，保存到已核实 UUID 的 Expansion 诊断目录。
   不是含机器人观测/动作的训练 episode。
6. 用户报告卡死并重启后，不再开新流；只做带节流的离线逐帧读回和方向预览。

日志中的流生命周期重叠约 60.21 秒；不同启动/停止时刻及帧间隔仍保留在原始日志。
